# 06. 技術選定の見直し

## 初期方針

開発初期は、M5Stack側の実装にUIFlowを利用していました。UIFlowは視覚的にプログラムを組めるため、短時間で画面や動作を試しやすい点がメリットでした。

## 発生した課題

機能が増えるにつれて、以下の課題が見えてきました。

### 拡張性

API通信、状態管理、画面切り替えなどを組み合わせると、ブロックベースの実装では見通しが悪くなりました。細かい制御を追加しようとすると、UIFlow上での管理が難しくなりました。

### 保守性

チームで修正を重ねる中で、どの処理がどこにあるのかを追いにくくなりました。特に通信処理や画面更新処理は、コードとして読める形の方が確認しやすいと感じました。

### 実装自由度

HTTP通信の例外処理、デフォルト値へのフォールバック、ボタン操作時の状態管理など、細かな挙動を調整する場面が増えました。MicroPythonを直接扱う方が、必要な処理を実装しやすいと判断しました。

### Git管理

UIFlowのファイルは差分が読みづらく、レビューや原因調査が難しい場面がありました。MicroPythonのコードとして管理することで、変更点を追いやすくなりました。

## 方針変更

チームで相談し、M5Stack側はMicroPythonコードを直接扱う方針へ移行しました。これにより、API通信や状態管理をコードとして整理しやすくなり、Web・サーバ側との連携も確認しやすくなりました。

## 学び

初期段階では試しやすさを優先する技術が有効ですが、チーム開発で機能が増える場合は、保守性や差分管理のしやすさも重要になります。技術選定は最初に決めて終わりではなく、開発状況に応じて見直す必要があると学びました。
